# Documented deviations from the Fortran implementation

Each entry: what differs, why, and the measured effect on verification.

## dispersion

Fortran solves L = L0·tanh(2πh/L) by damped golden-ratio fixed-point iteration
with **absolute** tolerance 1e-5 m (`iteratedispersion`,
wave_functions.F90:800-837). In deep cells (L ≈ 100 m) the iteration terminates
early: measured error of the Fortran wavenumber at 10 m depth, Trep=8 s is
**+1.9e-4 (0.2%)** vs the exact root.

The WebGPU model solves the same dispersion relation σ² = gk·tanh(kh) with
Newton iterations (warm-started from the previous k) to f32 machine accuracy
(measured |k−k_exact| ≈ 1e-9 at the same point). This is *more* accurate than
the reference; the residual H difference from this term is ≤ 0.05%.

## stationary wave solver: whole-grid relaxation vs row marching

Fortran (wave_stationary_directions.F90) marches row-by-row in +s, iterating
each row to `maxerror` with a per-row pseudo-timestep dtw (CFL of rows i−1..i+1,
progressively limited by the sink-stability bound 0.5·ee/dd). The WebGPU model
iterates the identical discrete operators over the whole grid in pseudo-time
until the same `maxerror`/`maxerror_angle` criteria hold globally (plus a
roller-convergence criterion Fortran lacks, see below).

Consequences:
- The discrete fixed point depends (weakly) on dtw because dissipation is
  evaluated at the post-advection intermediate state. The WebGPU model
  therefore reproduces Fortran's **per-row dtw** (same CFL window + sink
  limits, re-evaluated each iteration batch) rather than a global dtw. With
  this, H matches the default-tolerance Fortran run to 0.13% nRMSE, and a
  tight-tolerance Fortran run (maxerror=1e-5) to **0.04% nRMSE**.
- Fortran's H-convergence check can leave rows slightly under-converged at the
  default maxerror=1e-4 (measured: up to 0.2% H change when tightening
  Fortran's own tolerance). The WebGPU solution sits closer to the tight
  Fortran solution than default Fortran does.
- Iteration is red-black (even/odd rows alternating) Gauss-Seidel rather than
  Jacobi: plain Jacobi leaves an undamped odd-even mode in the roller energy
  (measured 1.6% sawtooth in R, 4% in Fx). Red-black eliminates it; Fx nRMSE
  0.32%.
- The WebGPU solver also requires the roller height change per iteration to
  drop below `maxerror` (Fortran only checks H and direction). This makes R/DR
  deterministic rather than dependent on however many iterations H needed.
- upwind_2 x-fluxes: at the *updated row's* right face under negative flow
  (seaward-propagating energy), Fortran's windowed call uses 1st-order upwind;
  replicated via statMode branch. Y-advection forced to upwind_1 as in
  Fortran:108-113.

## stationary solve scheduling

Fortran runs a stationary solve on the first timestep (t=dt, with taper
factor t/taper) and then every `wavint`. With flow disabled the WebGPU CLI
reproduces the same sequence but stops once the taper factor has reached 1
(further solves are identical). With flow enabled, solves run every wavint on
the current water level, as in Fortran.

## single_dir: the stationary directions sweep on the whole-grid relaxation (OCE-252)

`single_dir = 1` (Roelvink et al. 2018; XBeach's own 2-D default, which the
calling application overrides to 0) runs the stationary model on its own
direction grid (`dtheta_s`, every `wavint`) for the mean direction, and
propagates the wave groups in ONE instationary bin along it
(wave_timestep.F90:84-99, wave_stationary_directions.F90 callTypeDirections,
set_stationary_spectrum in waveparamsnew.F90:3077-3112). The port:

- The directions sweep is the stationary kernel set compiled a second time
  for `ntheta_s` bins (`DIRS = 1` in the WGSL preamble) over its own
  `ee_s` buffers, iterated with the whole-grid red-black relaxation of the
  section above to the same `maxerror`/`maxerror_angle` criteria (no roller
  criterion: the directions model carries no roller). Depths are the
  `wavint`-smoothed `hhws` (`update_means_wave_flow`, a kernel after
  `wavePrep` every step) everywhere Fortran's `hhwlocal` is, and the
  instantaneous `hhw` in the breaker, as `roelvink` reads `s%hhw`. Only
  `thetamean` survives the sweep; the instationary dispatches that follow
  recompute dispersion, E, H, D, Qb on `hhw`, as `wave_dispersion(s,par,0)`
  and `wave_instationary` do in Fortran.
- The stationary boundary spread `ee_s(1,:,:)` is generated by the wavemaker
  (`interp_using_trapez_rule` of the combined spectrum's Sd onto `theta_s`,
  times ρg) and carried on the condition as `esData`; on reuse it is read from
  `esbcflist.bcf`. The wavemaker's E table has one bin. Both match the Fortran
  tables of `verification/reference/rip2d_jons_sd1` to 1e-6
  (`test/singledir_parity.test.ts`). A single_dir run without an Es
  table refuses to start.
- **Scheduling.** The host-stepped CLI loop lands on every `wavint` hit and
  runs the sweep before that step's instationary update, at `t = dt` and on a
  new boundary condition, exactly as Fortran. The batched GPU loops (CLI
  `--gpudt`, the app worker) end a batch on each hit and run the sweep after
  the hitting step: one step (one `dt`) later than Fortran, on a field that
  changes over `wavint`. The smoothed depth the sweep sees is likewise the
  previous step's `hhws` (the update runs inside the instationary dispatches).
- **Iteration budget.** The sweep stops at `maxerror`/`maxerror_angle` or
  after max(6·(nx+1), `maxiter`) whole-grid iterations — the budget Fortran
  gives one row. On a real coast a few shoreline cells never settle to
  1e-4 in either engine (the Fortran Newport run logs "Wave propagation row
  92–97, iteration 500, H error .0015–.003"; the port's H error plateaus at
  3–7e-4 there), so the cap is what bounds the cost: six sweeps of 680
  iterations on the Newport hour (113×264) add 4 s to a 56 s run, measured
  on the laptop iGPU with `--gpudt`. Verified against the Fortran single_dir
  run on the same tables: H_mean 0.19 % nRMSE, zs_mean 0.14 %, and the
  sd1 − sd0 difference of both fields identical to Fortran's (r 0.999).
- `dtheta` in a single_dir case is read and ignored, as Fortran does (its
  log says "Unknown, unused"); the instationary bin spans thetamin..thetamax
  (params.F90:262); `dtheta_s` is required, as in Fortran.
- Not ported with it: wave-current interaction (`wci`, smoothed `uws/vws`), as
  for the rest of the solver.

## precision

The WebGPU model computes in f32 (WGSL has no f64); the reference is f64.
State layout is column-major (nx+1, ny+1[, ntheta]) matching Fortran, so
reductions occur in the same order where order matters. Measured f32 noise on
the stationary 1D case is well below the physics tolerances (H 0.13% is
dominated by solver-path differences above, not rounding).

## absorbing front boundary (`front = abs_2d`): incoming-wave term in closed form

`boundaryconditions.F90:1255` and `:1265-1275` build the reflected velocity
`ur` from the incoming long-wave flux through

    thetai = atan(vi/ui)
    ui*(cg*cos(thetai) - sqrt(g*h)) / (cg*cos(thetai))

The port evaluates the same quantity without the trigonometry. Since
`cos(atan(vi/ui)) = |ui| / sqrt(ui² + vi²)`, the term is identically

    ui - sign(ui)*sqrt(ui² + vi²)*sqrt(g*h)/cg        (freewave=1: ui - sign(ui)*sqrt(ui² + vi²))

Same mathematics, including the sign jump where `ui` crosses zero that the
Fortran form also has; no division, no `atan`, no `cos`. In f64 the trig form is
harmless. In f32 with hardware `atan`/`cos` (the WGSL/Vulkan precision floor is
an absolute error of 2⁻¹¹) a grazing incoming flux, |ui| ≪ |vi|, turns
`cos(thetai)` into noise of either sign and `ur` blows up in the offshore
column. `ui` crosses zero every long-wave period wherever `vi ≠ 0`, so every
2-D run visits the ill-conditioned region; forcing that enters the window at
grazing angles lives there (Oahu, Waimea, sea from 70°T on an edge facing
297°T: ~85 % of the energy outside the ±90° window, what enters hugging the
boundary).

Evidence (2026-10-19, Linear OCE-373): on that hour ~1 app run in 14 broke down
with NaN first in grid column 0, deterministic per wavemaker seed (seeds 10, 17,
29 of 1–40; Chrome and the Deno CLI, same Intel Xe2 GPU). Fortran on the same
spectrum: 6/6 clean with its own tables, clean on the port's seed-10 tables
written as reuse `.bcf` files; the port's and Fortran's tables are statistically
the same (per-bin energy, grazing-flux fraction 3.8–5.0 % vs 4.6 %). With the
closed form the three failing seeds run clean to 1200 s with the offshore edge
within 0.21 m of still water, and each of them compared against Fortran run
on the port's own tables (reuse files) passes the mission harness: every
mean field ≤ 0.02 % nRMSE (zs_mean ≤ 1.1 mm), snapshots ≤ 0.9 % except the
instantaneous H at 3.7–4.7 % (tolerance 5 %, the usual sensitivity of a
1200 s group-resolving snapshot). Not a tolerance, floor or clamp: the formula
is unchanged where it is well conditioned.

## lateral wave boundary

`lateralwave = wavecrest` (interpolation along the wave crest) is not yet
implemented; `neumann` (default) and stationary-solver lateral copies are.
Runs requesting wavecrest fail loudly rather than silently substituting.

## out-of-scope processes

sedtrans, morphology, avalanching, non-hydrostatic, groundwater, vegetation,
ships, drifters, rainfall, q3d are rejected at parameter parse time when
enabled. Fields they would contribute (e.g. Dveg in the dissipation
distribution, infil in continuity) are hard zero.

## Qb mean accumulators (E2, stage 2)

`Qb_mean`/`DR_mean` (slots 10-11) validate against Fortran varoutput means
on rip2d (roelvink_daly): DR/H/zs means exact (0.00-0.01% nRMSE, r=1.0000);
**Qb_mean 6.7% nRMSE, r=0.981**. Cause: daly's per-cell binary Qb switching
— f32 dt-sequence divergence changes the breaking duty cycle of band-edge
cells (the smooth D = Qb·2αE matched to 0.1% in stage 1, ruling out field
wiring). Impact on the surf-zone delineation is sub-cell edge jitter, well
inside the mandatory 0.02-0.10 threshold sensitivity band (B2 §2.4 step 9).

## spectral wavemaker (E1): TS port of waveparamsnew.F90

`src/wavemaker.ts` (+ `rng.ts`, `fft.ts`, `spectrum.ts`) ports the
wbcversion=3 surfbeat spectral boundary generator (`spectral_wave_bc`).
Deviations from the Fortran implementation:

1. **Synthesis IFFTs use Bluestein's algorithm, not Singleton's.** Fortran
   runs Singleton's mixed-radix `ifft(Gn)/sqrt(N)` then `Re(·N)` — a plain
   unnormalized inverse DFT of even length `tslen`. The TS port evaluates
   the same sum with Bluestein's chirp transform on radix-2 FFTs
   (`fft.ts idftRealAdd`), valid for any `tslen`; the tables agree with the
   direct sum to rounding error (relative 1e-13). Until OCE-288 the sum was
   evaluated directly per nonzero bin, which cost O(K·tslen) per series and
   took 96 % of the generation time. The Hilbert envelope is a separate
   transform, where Fortran itself zero-pads to the next
   power of two — replicated exactly (radix-2). The Fortran frequency
   inconsistency is carried over: time oscillation on Fourier bin
   `Findex(i)`, spatial phase on `kgen(fgen)`.
2. **RNG.** Park–Miller/Schrage in exact integer f64 arithmetic:
   bit-identical draw streams for `random=0` (fixed seed 100). `random=1`
   seeds from `Date.now()` — Fortran's `SYSTEM_CLOCK` semantics differ, so
   `random=1` gives statistical parity only, never bit parity.
3. **`dtchanged` q-interpolation.** When the internal time step is reduced
   (`dtin < dtbc`), Fortran's `qinterp` fills only 3 of the 4 quarters and
   leaves the η quarter undefined; the TS port interpolates all four. The
   engine never reads the η quarter, so behaviour is unchanged — the written
   table is simply well-defined.
4. **v1 scope.** Single spectrum location (`nspectrumloc=1`; `Sfinterp`
   alongshore-constant — per-point phases still vary, so alongshore group
   structure survives for oblique seas) and a single condition block per run
   (`lastwaveelevation` starts from zeros; `rt` must cover the run, so the
   app worker sets it to `tstop`, beyond the 7200 s the Fortran keyword
   allows when the run is longer — no successive blocks, by decision,
   OCE-288). `nspectrumloc>1` and
   `wbcversion<3` error loudly. CLI file parsing covers JONSWAP parameter
   files (wbctype=parametric); swan/vardens case files still require
   pre-generated bcf tables (reuse), while the app ships SWAN/Datamesh
   spectra as in-memory tables through the solver API. Generation cost is
   about 2 s for a one-hour block at ny≈90 and grows linearly with ny; the
   bound-wave pair sums, O(K²) per boundary point, are what is left.
5. **App policy: `wbcScaleEnergy=0` on spectral forecast runs.** The engine
   default (1) mirrors Fortran — admitted-sector energy is rescaled back to
   the full input Hm0 — and stays in place for verification. The calling
   app passes 0: rescaling would re-inject the energy WaveClock reports as
   excluded ("N % of the wave energy enters the model window"), so the
   boundary forcing carries the admitted energy only and `admittedFraction`
   remains the single reconciliation number between offshore Hs and boundary
   variance.
6. **File reuse takes precedence.** When `ebcflist.bcf`/`qbcflist.bcf` exist
   in a case dir the CLI still reads them (byte-identical forcing for every
   existing verification case); generation only triggers when they are
   absent.

### Measured parity (2026-08-10 verification)

Deterministic parity, `random=0` seed 100, fixture
`verification/cases/surfbeat1d_jons_r0` vs a freshly generated Fortran
reference (`verification/reference/surfbeat1d_jons_r0`, xbeach-ref Docker
image):

- **Tier-1 tables**: E max rel diff 3.8e-9, q 6.6e-9 (qx 6.0e-9,
  qy 5.8e-9, qtot 6.6e-9, eta 7.2e-9); Trep 7.31773, Hrms 0.70710,
  theta0 0.005 match the Fortran-printed precision. Wavemaker internals
  (fgen/kgen/phigen) are bit-exact; the residual ~3e-8 in Sf/Eforc traces
  to SINGLE-precision literals (0.07/0.09 sigma) inside Fortran's own
  `jonswapgk` (waveparamsnew.F90:917-925) — the TS port is full double.
- **Tier-3 end-to-end** (GPU run, TS-generated tables vs the Fortran
  reference, identical realization): zs_mean 0.007 %, zs_var 0.608 %
  (tol 3 %), H_mean 0.041 %, u_mean 0.409 %, ue_mean 0.241 %,
  urms_mean 0.063 %, r >= 0.9997 — at the validated reuse path's own
  level. The reuse path itself is sha256-bit-identical before/after the
  wavemaker landing.
- **Statistical equivalence, `random=1`**: 20 TS seeds vs 6 Fortran
  realizations — Hm0 recovery max 0.025 %; IG-band envelope variance and
  var(qx) statistically indistinguishable (Welch t = -0.63 / -0.17).
  Note: Fortran's own var(qx) realization scatter is ~17 % rel std
  (direction draws enter the Okihiro coefficient), so single-draw
  comparisons against one fixture realization are NOT a valid parity
  test — compare distributions, or use `random=0`.
- **Boundary-depth trap**: XBeach copies zb row 2 onto row 1 at init
  (initialize.F90:248; mirrored in grid.ts), so the effective boundary
  depth of surfbeat1d_jons is bed.dep column 2 (7.9644 m), not column 1
  (8.0 m). A constant-8 fixture fails q parity by a uniform ~0.6 %.

## grid rotation: alfa held at 0, dir0 pre-rotated by the app

XBeach places rotated grids in world coordinates via `alfa` and interprets
`dir0` as a world-frame nautical coming-from direction (degrees CW from true
north). The engine ports that machinery (grid/theta rotation, wind), but the
`alfa != 0` path has no validation coverage here, so app-generated params
always set `alfa = 0` (grid frame = world frame) and instead pass a `dir0`
already rotated into the grid frame: degrees coming-from as if grid +x were
east. The single audited conversion lives in
the calling application; UTM meridian convergence is included
implicitly because domain corners are lon/lat (see the module header). The
`thetamin/thetamax` sector stays grid-relative (`thetanaut = 0`), consistent
with this frame.

## index helper `at()` written as an integer dot product (driver workaround)

Not a physics deviation — recorded because it is a construct chosen for a
compiler, not for the model. `src/shaders/common.ts` defines
`at(i, j)` as `dot(vec2<i32>(i, j), vec2<i32>(1, N1))` instead of
`i + j * N1`. Both are the same 32-bit integer (identical overflow); no
native shading language has an integer dot, so Tint (Chrome), WebKit and
naga (Deno) all lower it to a multiply-add — a code shape Apple's Metal
compiler on Intel gen-9 GPUs compiles correctly, where the plain form made
`at(i - 1, j)` read −1 (timestep collapse at t = 1 s on every bathymetry;
wrong `zs` in ~1000 cells). Evidence and fix: commit acab1cd (reporter's
Iris Plus 645, macOS 15, Chrome 152 + Deno), 2026-09-22.

Measured effect elsewhere (Linux/Vulkan, Intel Xe2-LPG, 2026-09-26):
verification 19/19 against the Fortran references, unchanged; WebGPU outputs
equal to the previous build within the engine's own run-to-run noise (the same
21 of 340 output files — rip2d and three thetamean — differ between two runs
of the previous build, by the same magnitudes, ≤ 0.63 % of range per cell in
Qb_mean and ≤ 0.1 % elsewhere); benchmark ms/step within ±2 % on every grid,
no consistent direction. Do not "simplify" it back. `at3()` keeps the plain
form: the reporter's per-kernel differential test found no kernel that
disagrees after this change.
